# Implementation assessment (RTM and Gap report)

How to decide, for each requirement, whether the current codebase implements it, whether that's verified, and whether
it's deployed, with evidence a reviewer can click.

## 1. Record the scope first (RTM §2, Gap §2)

Date; repository; branch/tag and **commit SHA** (put it in `PROJECT-CONTEXT.md` `repo_ref` so links are permalinks);
which artifacts you inspected and which you couldn't. Inspect, where available:

| Artifact | Typical evidence it gives |
|---|---|
| Requirements, product docs, tickets | intended behaviour, priorities, decisions |
| Source code (UI, services, batch) | Code evidence: file + symbol, endpoint, handler |
| Configuration, feature flags | whether the code path is active |
| DB schema, migrations | data requirements (DR), constraints |
| API definitions (OpenAPI, AsyncAPI, proto) | interface requirements (IFR) |
| Tests (unit, integration, E2E) and test reports | Verification evidence |
| CI/CD workflows and run results | whether tests run and pass on the assessed commit |
| Deployment config, release notes, environment manifests | Runtime/deployment evidence |

If something can't be accessed, say so, and mark the affected rows **Not verifiable** (code, verification or runtime, as appropriate).

## 2. Assess each row

For each requirement: read its acceptance criteria, then search for the implementation (routes/endpoints, service methods,
batch steps, schema objects, UI components named after the capability). Then fill in the row:

| Column | How |
|---|---|
| Code status | **Implemented**: code covers every acceptance criterion and flow. **Partially implemented**: some behaviour exists, at least one criterion/flow is missing (name it in Gap). **Not implemented**: nothing found after searching (say where you looked). **Blocked**: depends on a named unresolved decision/dependency. **Not applicable**: out of this codebase's scope or retired. **Not verifiable**: can't tell from what's available. |
| Code evidence | Links to the exact lines (`path:start-end` then `docver.py linkify`) plus the symbol: `` [`src/.../AccountService.java:40-88`](…) `updateAccount()` `` |
| Verification status | **Verified**: a test exercises the acceptance criteria and evidence shows it passes (CI run, report). **Partially verified**: tests cover some criteria. **Not verified**: no test, or tests not run. **Not verifiable**: no access to results. |
| Verification evidence | Test file/name links + CI run link/result. A test that exists but has no run evidence = Not verified. |
| Runtime status | **Deployed**: release/rollout evidence shows the commit (or later) in the stated environment. **Partially deployed**: some environments or behind a flag. **Not deployed** / **Not verifiable**. Never infer deployment from code. |
| Gap / remaining work | The specific missing behaviour or evidence ("no lockout after 3 failed attempts (AC-2)"; "no test for rounding") |
| Next action | Concrete: implement X, write test Y, decide Z (owner), investigate W |
| Confidence | High / Medium / Low + reason ("High: single code path, test covers all ACs"; "Low: dynamic dispatch, no tests") |

## 3. What doesn't count as implementation

Treat each of these as incomplete unless other evidence shows it meets the requirement: a UI element with no working
backend; TODO/FIXME; stubs, mocks, fakes or hard-coded responses; code behind a disabled flag; commented-out code;
an unreachable or untested path; an interface without an implementation; a migration that's written but not applied;
a passing test that doesn't assert the acceptance criterion.

## 4. Conflicts, duplicates and drift (RTM §5)

- Two requirements that contradict each other → recommend which wins and who decides.
- Duplicates → recommend merging (retire one ID and point it to the survivor).
- Code that behaves differently from the requirement → Code status Partially/Not implemented with the difference in Gap.
  **Don't edit the requirement to match the code**; raise a decision if the code behaviour might be the desired one.

## 5. Gap report (executive)

Built on the RTM, two pages, everything cites RTM IDs:

1. Scope, date, commit, evidence inspected (§2).
2. Counts by document and status (§3) and implemented-but-not-verified (§4): generated by `docver.py rtm summary`.
3. Highest-impact gaps and risks (§5): Must-priority gaps first, then risk to dates, compliance and data.
4. Blocking dependencies and decisions (§6), each with an owner.
5. Recommended next-milestone work (§7), ordered: name the RTM IDs each item closes and the evidence that will show it is done.
6. Limitations (§8): what wasn't inspected, Not verifiable rows, assumptions.
7. Open decisions and next actions (§9).

No completion percentage unless priorities are agreed. With agreed priorities, `rtm summary --weighted` prints the
formula (Must 3, Should 2, Could 1; Implemented 1, Partially 0.5; Not applicable excluded) and the figure covers code
only, not verification or deployment. Say that next to the number.

## 6. Practicalities

- **Unbuilt items:** a requirement with no code is `Runtime: Not deployed`, not Not verifiable. Not verifiable is for things that may
  exist but can't be checked.
- **Bulk entry:** write the assessments as JSON (`{"BR-001": {"Code status": "...", "Code evidence": "cbl/X.cbl:10-20 PARA", ...}}`) and run
  `docver.py rtm apply <folder> --from assessments.json`, then `linkify`. It's safer than hand-aligning a 13-column table.
- **Missing analysis notes:** if the BRD cites `docs/analysis/rules/*.md` or program cards that aren't in the repo, don't rebuild the
  knowledge base just for the assessment. Follow the BRD's own source links to the code, and note in RTM §2 that the notes were unavailable.
- **Platform defaults** (for example CICS `STARTBR` positioning GTEQ by default, or COBOL truncation without `ROUNDED`) can decide whether a
  rule holds. When a status depends on one, say so in Confidence.
- **Requirements vs rules:** `rtm summary` reports BRs and RULs separately; keep them apart in the gap narrative too.

## 7. Legacy-only codebase (no target code yet)

When the repository holds only the legacy system and the BRD describes the target state, say so in the first line of RTM §2 and of the
gap report: **this is a baseline assessment**. "Implemented" then means *the legacy system already does this* (behaviour to reproduce or
deliberately change), not *migrated*. Proposed requirements the legacy doesn't meet are Not implemented, transition requirements
(migration, equivalence) are Not implemented until their tooling exists, and nothing counts as migrated progress.

## 8. Legacy migration variant

When assessing a migration in progress, the "current codebase" is the new React/Spring Boot code. Use the legacy
references in each FR (linked legacy lines) to judge equivalence, and treat functional-equivalence test results as
verification evidence. Legacy-only behaviour that no requirement covers goes to RTM §5 as a possible missing requirement.
